## 1. ОБЩИЕ СВЕДЕНИЯ

**1.1 Наименование:** автоматизированная система поддержки составления смет на базе локально развёрнутой LLM («Нейро-сметчик»).

**1.2 Назначение:** снижение трудозатрат сметчика на рутинные операции при сохранении **полного контроля человека** над финальным утверждением документа; рост скорости и консистентности расчётов.

**1.3 Цели:**
- сократить время составления черновика на 60–80 %;
- снизить число технических ошибок (пропуски позиций, арифметика);
- формализовать экспертизу сметчиков в базе знаний;
- обеспечить **полную локальность** обработки (без передачи третьим лицам).

**1.4 Область применения:** [заполняется заказчиком: ремонт квартир / коммерческое строительство / иное]. В MVP — внутренняя отделка жилых и коммерческих помещений.

## 3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 3.1 Пользовательский сценарий (User Flow)

```
1. Пользователь вводит запрос (текст / голос / фото объекта)
2. Clarification Loop: уточняющие вопросы при неполноте данных
3. Система генерирует черновик сметы
4. Позиции с низкой уверенностью помечаются для проверки человеком
5. Сметчик проверяет, корректирует, утверждает смету
6. Формируется итоговый документ (Excel / PDF)
7. При необходимости — Revision Loop (правки клиента)
8. После завершения проекта — Plan-Fact Loop (сверка план/факт)
```

### 3.2 Микросервисы

#### 3.2.1 Parser Service
Извлечение структурированных параметров из естественно-языкового запроса (опционально — изображение). Выход — JSON со строгой схемой: тип помещения, площадь, вид работ, ограничения, регион, срочность, бюджет. Обязательны: валидация по схеме, retry ≤3 попыток с передачей ошибок в следующую попытку, логирование **всех** попыток (`pipeline_execution_log`, `llm_inference_log`). При недоступности GPU — детерминированный rule-based fallback.

#### 3.2.2 Clarification Service
≤5 итераций вопрос–ответ; вопросы только по отсутствующим критичным полям (`area_m2`, `room_type`, `work_scope`, `region`); пользователь может прервать диалог — система продолжает с дефолтами и явной пометкой в смете. Таймаут ожидания → Notification Service и отложенная обработка.

#### 3.2.3 Search Service
Гибридный поиск: semantic (vector) + keyword. SLA p95 ≤500 мс на запрос, top-N кандидатов с метрикой релевантности и разбиением score на semantic/keyword компоненты.

#### 3.2.4 Matching Service
Confidence score для каждого сопоставления: **≥0.85 — авто-принятие; 0.5–0.85 — расширенный повторный поиск; <0.5 — эскалация на ручную проверку**. Неоднозначные однословные формулировки и размытые запросы не могут быть авто-приняты. Результат обязан ссылаться на реальный `catalog_id`.

#### 3.2.5 Calculation Service
**Запрет LLM для вычислений.** Только `Decimal`, настраиваемые наценки/коэффициенты/НДС, независимый пересчёт контрольной суммы вторым методом (целые копейки + `Fraction`). Контрольная сумма связывает позиции, каталог и итоги.

#### 3.2.6 Validation Service
Аномальные цены относительно исторических данных, дубли позиций, полнота по типовому составу работ из архива, проверка контрольной суммы, опциональный LLM-ревью (judge-паттерн). Ошибки уровня `error` блокируют утверждение.

#### 3.2.7 Document Service
Excel (.xlsx) с фирменным шаблоном, PDF (кириллица), опционально экспорт в формат, совместимый с Гранд-Смета/АРПС. Цветовая индикация confidence. В неутверждённом документе — явная пометка «ЧЕРНОВИК».

#### 3.2.8 Revision Service
Обработка **дельты** (add/update/remove), автоматическое версионирование (immutable history), diff-view между версиями. Утверждённая смета неизменяема.

#### 3.2.9 Orchestrator
Детерминированная последовательность вызовов без свободного агентного поведения LLM; trace_id, retry с экспоненциальной задержкой, circuit breaker, история попыток/ошибок каждого шага, настраиваемые пороги эскалации, fallback в ручной режим.

#### 3.2.10 Vision/OCR Service *(v1.1)*
Отдельная мультимодальная модель (Qwen2.5-VL) или OCR-движок; JSON с привязкой к справочнику дефектов/объектов; confidence для каждого элемента; blur detection / контроль освещения → деградация в ручной ввод; защита от EXIF/visual prompt injection.

#### 3.2.11 Notification Service *(v1.1)*
Каналы: внутренний UI, email, опционально корпоративный мессенджер. Приоритизация (эскалация по низкому confidence — высокий приоритет), подписки по ролям, SLA реакции ≤30 с.

#### 3.2.12 Prompt Management Service *(v1.1)*
Промпты вне кода, версионирование, привязка версии к каждому исполнению пайплайна, откат без деплоя, canary-тестирование на доле трафика, A/B-сравнение на golden set.

### 3.3 Циклы обратной связи (обязательные)

| № | Цикл | Периодичность | Назначение |
|---|---|---|---|
| 1 | Валидация внутри пайплайна | Каждый запрос | Контроль качества генерации |
| 2 | Clarification Loop | Каждый запрос (при неполноте) | Сбор недостающих данных |
| 3 | Revision Loop | По запросу | Обработка правок |
| 4 | Feedback Loop | Непрерывно | Накопление данных для обучения (`llm_corrections`) |
| 5 | Data Freshness Loop | Еженедельно | Актуализация цен каталога |
| 6 | Model Drift Loop | Ежедневно | Мониторинг деградации на golden set |
| 7 | Plan-Fact Loop | После проекта | Калибровка коэффициентов |
| 8 | Инфраструктурный retry | При сбоях | Отказоустойчивость |

### 3.4 API-контракты между микросервисами *(v1.1, см. Приложение Г)*

- REST/gRPC, JSON, OpenAPI-спецификация обязательна для каждого сервиса.
- Каждый межсервисный запрос несёт `trace_id`; все ответы LLM-сервисов логируются целиком (вход, выход, версия промпта, версия модели, confidence, trace_id) в `llm_inference_log`.
- Таймауты и retry задаются Orchestrator; версионирование API (`/v1/`) с первого релиза.
- Единый формат ошибки: `{"detail": "...", "code": "..."}`.

## 4. ТРЕБОВАНИЯ К ИНФРАСТРУКТУРЕ

**4.1** Полностью локальное развёртывание, без внешних облачных LLM-провайдеров.

**4.2 Аппаратные требования**

| Параметр | Минимум | Рекомендуется (прод) |
|---|---|---|
| GPU | 1× RTX 4090 / A6000 (24–48 ГБ) | 2–4× A100 80 ГБ |
| RAM | 128 ГБ | 512 ГБ |
| CPU | 32 ядра | 64+ ядра |
| Хранилище | NVMe SSD 2 ТБ | NVMe SSD 8 ТБ+, RAID |
| Сеть | 1 Gbps | 10 Gbps |

**4.3 Стек:** vLLM/TGI (OpenAI-совместимый API), Qwen2.5 (7B/32B/72B каскадом), Python + FastAPI, Celery/RQ + Redis, PostgreSQL 15+, Qdrant, MinIO, Prometheus + Grafana, Docker Compose / Kubernetes.

**4.4 Сетевая изоляция:** блокировка исходящего трафика к внешним AI-API на firewall; сегментация DMZ / Application / Data; VPN для удалённой работы. Проверка хоста инференса на старте приложения; при нелокальном хосте вызовы запрещены.

**4.5 Среды:** Dev → Staging → Production с раздельным релизным процессом для **кода, промптов, весов модели и базы знаний**. Продвижение релизов только после golden-регрессии не хуже baseline −2 %.

## 5. ТРЕБОВАНИЯ К МОДЕЛИ ДАННЫХ

**5.1 Сущности:** `smetas`, `smeta_versions`, `smeta_positions`, `price_catalog`, `clarification_sessions/turns`, `llm_corrections`, `golden_examples`, `plan_fact_comparison`, `historical_correction_factors`, `pipeline_execution_log`, `security_audit_log`, `knowledge_base_versions`, `users`, `roles`, `notifications`, `prompt_versions`, `model_versions`, `llm_inference_log`, `vision_extraction_results`, `rate_catalog_sources`, `documents`, `drift_checks`, `data_freshness_log`, `estimate_events`.

**5.2 Принципы:** сметы не перезаписываются — только новые версии; все деньги `DECIMAL`/TEXT-строка Decimal; каждая позиция обязана ссылаться на реальную запись `price_catalog`; для критичных сущностей — Event Sourcing (`estimate_events`); append-only триггеры на версиях, позициях, LLM-логе и аудите. `llm_inference_log` хранится отдельно, доступ ограничен (ML-инженер, безопасность), retention ≥12 мес., затем холодный архив.

**5.3 Резервное копирование:** ежедневный full backup PostgreSQL + непрерывный WAL, снапшоты Vector DB, backup весов и конфигурации, **RPO ≤1 ч, RTO ≤4 ч**, периодическое тестирование восстановления.

## 6. ТРЕБОВАНИЯ К БЕЗОПАСНОСТИ

**6.1 LLM-угрозы:** разделение system/user ролей, детекция паттернов injection и отказ в обработке, строгая валидация выхода по схеме, только синтетические/анонимизированные few-shot примеры, обязательная ссылка позиции на каталог, защита от извлечения системного промпта.

**6.2 Классическая ИБ:** RBAC (клиент / сметчик / руководитель / администратор), MFA для руководителя/администратора, AES-256 at rest и TLS 1.3 in transit, секреты в Vault, append-only аудит всех действий.

**6.3 Compliance:** 152-ФЗ (локальность), политика хранения/удаления, немедленный отзыв доступа при увольнении.

**6.4 Защита интеллектуальной собственности:** NDA для доступа к промптам/весам, ролевое ограничение доступа к исходным текстам промптов.

**6.5 Внутренние угрозы:** «четыре глаза» для смет выше порога суммы, мониторинг аномальных отклонений от стандартных цен.

**6.6 Защита от злоупотреблений *(v1.1)*:** rate limiting на API Gateway, ограничение размера файлов, проверка MIME по magic bytes, антивирусное сканирование, санитизация текста (управляющие символы, скрытые инструкции в EXIF).

**6.7 Лицензирование моделей *(v1.1)*:** проверка лицензии open-weight модели (Qwen2.5 — Apache 2.0 / Qwen License в зависимости от версии) на коммерческое использование; фиксация хэша весов в `model_versions` для воспроизводимости.

## 7. ТРЕБОВАНИЯ К БАЗЕ ЗНАНИЙ

**7.1 Источники:** внутренние прайс-листы, нормативные базы ГЭСН/ФЕР (при наличии прав), архив смет за 2–3 года, регламенты расчёта наценок/коэффициентов.

**7.2 Обработка:** нормализация единиц и форматов цен, дедупликация через semantic similarity, обогащение метаданными (категория, синонимы, типовые сочетания), smart chunking с overlap.

**7.3 Контроль качества:** пропущенные цены, аномалии, покрытие категорий, тестовый прогон поиска на эталонных запросах.

**7.4 Юридические требования:** проверка правового статуса источников нормативов до парсинга; при необходимости — лицензионный договор.

**7.5 Актуальность:** еженедельный регламент обновления цен (Data Freshness Loop), ежеквартальная ревизия полноты.

## 8. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

**8.1 Производительность:** черновик ≤60 с (p95), p99 ≤120 с; ≥[N] одновременных пользователей (уточняется); очередь задач при пиковой нагрузке.

**8.2 Отказоустойчивость:** fallback при недоступности GPU (ручной режим), circuit breaker в Orchestrator, retry с экспоненциальной задержкой.

**8.3 Масштабируемость:** горизонтальное масштабирование Application Layer, мультитенантность для филиалов, региональные коэффициенты цен.

**8.4 UX:** цветовая индикация confidence, diff-view, ввод текста/голоса/фото, базовые WCAG-критерии (focus-visible, aria-live, контраст, масштабирование).

**8.5 Стратегия тестирования *(v1.1)*:** см. [test-strategy.md](test-strategy.md). Уровни: unit, contract/integration, E2E на golden set, регрессия качества LLM (baseline −2 %), нагрузочное, red teaming по OWASP LLM Top-10, chaos engineering в Staging. **Критерий готовности к релизу:** все уровни пройдены, регрессия не хуже −2 %.

## 11. ЭКОНОМИЧЕСКОЕ ОБОСНОВАНИЕ

**CAPEX:** GPU-инфраструктура (или аренда выделенного GPU), разработка MVP, лицензии нормативных баз.
**OPEX:** электричество/обслуживание, команда поддержки, регулярная актуализация базы знаний.
**ROI:** экономия времени на смету × число смет в месяц + снижение потерь от ошибок; точка окупаемости рассчитывается индивидуально.

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Open-weight LLM уступает коммерческим API | Высокая | Среднее | Fine-tuning, каскад моделей, промпт-инженерия, rule-based fallback |
| Сопротивление персонала | Средняя | Высокое | Поэтапный rollout, вовлечение скептиков |
| Высокий CAPEX на GPU | Высокая | Высокое | Аренда выделенного GPU на старте |
| Низкое качество базы знаний | Высокая | Высокое | MVP на 20–30 % позиций по Парето |
| Дрейф модели | Средняя | Среднее | Golden set + ежедневный drift check |
| Юридические риски нормативов | Низкая-средняя | Высокое | Юридическая проверка до парсинга |
| Переоценка confidence матчером | Средняя | Высокое | Calibration на golden set, эскалация размытых формулировок |
